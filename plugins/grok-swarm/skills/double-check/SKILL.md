# Double Check

Use this skill to deliberately slow down the final mile and test whether the work is actually complete.

## Workflow

1. Restate the goal in concrete terms.
   - Include what the user originally asked for.
   - Include any newest user corrections, stop conditions, or constraints.
   - Define what "complete" means for this task.

2. List the verification angles before inspecting.
   Choose the relevant angles for the task, such as:
   - User-visible behavior
   - Data correctness and edge cases
   - Security, privacy, and tenant isolation
   - Error handling and recovery
   - Tests and validation coverage
   - Build, lint, typecheck, and runtime behavior
   - Documentation, migration notes, and operational impact
   - Adjacent code paths that could share the same bug pattern

3. Check from each angle.
   - Use source inspection, tests, logs, browser checks, or command output as appropriate.
   - Prefer concrete evidence over reassurance.
   - Treat TODOs, placeholders, no-op handlers, fake success states, and unverified assumptions as suspicious.
   - For code changes, inspect the actual diff and any files generated by validation commands.

4. Fix what is definitely wrong when the user asked for implementation or when the bug is adjacent and actionable.
   - Keep changes scoped to the discovered issue.
   - Do not silently widen into speculative refactors.
   - Do not declare success until the new fix has its own verification.

5. Report the result.
   - If complete: say why, with the key evidence.
   - If incomplete: list remaining blockers or risks plainly.
   - Separate verified facts from assumptions.
   - Mention validation commands that could not run and why.

## Recursive Double-Checks

When double-checking a previous double-check, inspect the earlier pass itself:

- What angles did it omit?
- Did it rely on stale memory, unrun tests, optimistic assumptions, or screenshots without interaction?
- Did it verify the exact user-facing path?
- Did fixes introduce new mismatches, generated drift, or broken tests?
- Are the final claims stronger than the evidence supports?

## Output Shape

Keep the final answer concise and evidence-led:

```markdown
Double-check result: complete / incomplete / partially complete

Verified:
- ...

Fixed:
- ...

Remaining risk:
- ...
```

Omit sections that do not apply.
